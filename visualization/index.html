de.dhbw.ctf · VaultAccess

Wie VaultAccess wirklich verriegelt ist

Ein Rundgang durch vault.jar: Build-Pipeline, Laufzeit-Kontrollfluss und die eine kryptographische Schwachstelle, die den ganzen Mechanismus trägt.

Build-Pipeline

Vom Quelltext zur ausgelieferten JAR

build.sh durchläuft acht Schritte. Crypto wird obfuskiert und anschließend byteweise "verschlüsselt"; Main wird nur obfuskiert, bleibt aber normal ladbar — sie muss es sein, denn die JVM startet über sie.

1
Secret & Flag vorverschlüsselnbuild.sh
Python-Vorlauf berechnet _S (Secret, XOR-kodiert) und _F (Flag, keystream-verschlüsselt) neu und schreibt sie direkt in Crypto.java, bevor kompiliert wird.
2
KompilierenMain, VersionInfo, RuntimeTag, Crypto
In einem Durchgang, weil Crypto._secret() jetzt direkt Main.EncryptedClassLoader._key() referenziert — eine echte Compile-Zeit-Abhängigkeit, keine Reflection.
3
Main obfuskierenproguard/main.pro
ProGuard benennt private Felder/Methoden um, entfernt Debug-Infos, schreibt ein Mapping heraus (-printmapping), das der nächste Schritt braucht.
4
Crypto obfuskierenproguard/crypto.pro
Wendet das Mapping aus Schritt 3 an (-applymapping), damit Crypto.class dieselben verschleierten Namen für Main/Main$a referenziert wie das tatsächlich ausgelieferte Main.class. Die sechs öffentlichen Methoden a()–f() bleiben unverändert — Main ruft sie per Reflection mit Namen auf.
5
Crypto.class "verschlüsseln"Byte-Reverse + XOR
Array spiegeln, jedes Byte mit dem Loader-Schlüssel XOR-en → landet als Crypto.class.encrypted im JAR. Derselbe Schlüssel, den Main.EncryptedClassLoader._key() zur Laufzeit berechnet.
6–8
Manifest schreiben, packen, synchronisieren
Manifest bekommt X-Build-Tag und X-Secret-Tag — zwei zur Build-Zeit fixierte Werte, die Teil der Laufzeit-Schlüsselableitung werden.
Laufzeit

Der Kontrollfluss von main()

Sieben Schritte vom Programmstart bis zur Flag-Ausgabe — jeder Aufruf an Crypto läuft über Reflection, nie über einen direkten Methodenaufruf.

1
Argumente prüfen. Kein Argument oder --help → Hilfetext, Programmende.
2
EncryptedClassLoader loader = new EncryptedClassLoader(...);
Class<?> crypto = _resolveClass(loader, _CCand, _MaCand);
_resolveClass() probiert fünf Klassennamen-Kandidaten der Reihe nach per loadClass() durch. Zwei davon (CacheLoader, ConfigStore) sind echte, ladbare Decoy-Klassen — sie laden erfolgreich, besitzen aber nicht die erwartete Methodensignatur. Zwei weitere sind reine XOR-Lockvögel, die schon in loadClass() mit ClassNotFoundException scheitern. Deshalb prüft _resolveClass() zusätzlich per _MaCand, ob getMethod(..., byte[].class) auf der geladenen Klasse trifft, bevor sie akzeptiert wird — erst dieser Treffer (bei "de.dhbw.ctf.Crypto") löst findClass() aus → entschlüsselt Crypto.class.encrypted mit dem Loader-Schlüssel.
3
--sample: ruft Crypto.d() (Beispiel-Nachricht, hex) und Crypto.e() (deren MAC) auf, druckt beides, Programmende. Kein Secret nötig auf Aufruferseite — die App liest ihr eigenes eingebettetes Secret selbst.
4
String expectedMac = crypto.a(messageBytes);
if (!expectedMac.equalsIgnoreCase(inputMac)) → "Access denied. Invalid MAC."
Zwei-Argument-Modus: Crypto.a() berechnet den MAC für die eingereichte Nachricht neu und vergleicht ihn mit dem übergebenen. Akzeptiert jede Nachricht, für die der Aufrufer einen passenden MAC liefert.
5
boolean formatOk = crypto.g(messageBytes, inputMac);
if (!formatOk) → "Access denied. Integrity check failed."
Sieht aus wie ein zweiter, unabhängiger MAC — läuft auf jedem regulären Pfad und kann den Prozess beenden. Prüft aber nur strukturelle Invarianten (Digest-Länge, Hex-Zeichensatz, eine Bit-Tautologie), die an dieser Stelle immer erfüllt sind. Kein Secret involviert, keine echte Sicherheitswirkung.
6
String role = crypto.b(messageBytes);
Rollenprüfung nach der MAC-Prüfung, auf denselben Bytes. Gibt das letzte user=-Feld zurück — auch wenn diese Bytes durch Length-Extension um ein zweites &user=admin verlängert wurden.
7
role.equals("admin") → Access granted. + Crypto.c() (Flag, aus dem Secret abgeleitet entschlüsselt). Sonst Access denied. You are: <role>.
Zwei unabhängige Schichten

Verschleierung schützt den Weg dorthin — nicht das Ziel selbst

Die Anwendung hat zwei völlig getrennte Mechanismen. Nur einer davon ist ein echtes kryptographisches Problem.

verzögert, bricht nicht

Verteilter Loader-/Secret-Schlüssel

key = SHA256(f1 ‖ f2 ‖ f3 ‖ f4)[0:4]

Vier Fragmente — Bytecode-Konstanten, Manifest-Attribute, ein zweiter Methodenaufruf — werden per SHA-256 zu einem Schlüssel verdichtet, mit dem Crypto.class.encrypted bzw. das eingebettete Secret entschlüsselt werden. Alle Fragmente liegen unverschlüsselt in derselben JAR.

verzögert, bricht nicht

Kandidaten-Reflection + ladbare Decoy-Klassen

getMethod(candidate) für candidate in Kandidaten

Klassen- und Methodennamen liegen nicht als eine globale XOR-Formel vor, sondern als Listen von Kandidaten mit unterschiedlichen Schlüsseln. Zwei Kandidaten (CacheLoader, ConfigStore) sind echte, ladbare Klassen ohne die passende Methodensignatur — reine Druckbarkeit der decodierten Strings reicht nicht mehr, um den echten Kandidaten zu erkennen.

verzögert, bricht nicht

Fake-Sekundärprüfung Crypto.g()

bitCount(x) ≤ 32 — für jeden int immer wahr

Läuft auf jedem regulären Pfad zwischen MAC- und Rollenprüfung und kann den Prozess beenden — sieht aus wie ein zweiter, unabhängiger MAC. Prüft aber nur strukturelle Invarianten, die an dieser Stelle ohnehin erfüllt sind. Kein Secret involviert, keine echte Sicherheitswirkung.

echte Schwachstelle

Secret-Prefix-MAC

MAC = SHA256( secret ‖ message )

SHA-256 ist Merkle–Damgaard-basiert: der Hash-Output ist der komplette interne Zustand. Das ist der eigentliche Lerninhalt der Aufgabe — Details in Tab 2.

Diagnose

Ein Secret-Prefix-MAC ist kein MAC

Bruchstelle

SHA256(secret ‖ message) statt HMAC

MAC(m) = SHA256( secret ‖ m )

SHA-256 verarbeitet Daten in 64-Byte-Blöcken. Der 32-Byte-Output nach dem letzten Block ist der komplette interne Zustand — er wird nicht weiter verdichtet oder verschlüsselt. Wer SHA256(secret‖message) und die exakte Bytelänge von secret‖message kennt, kann daraus den Zustand rekonstruieren und nahtlos weiterrechnen, als hätte man secret‖message‖padding‖suffix gehasht — für ein selbst gewähltes suffix, ohne secret je gesehen zu haben.

Das ist die Hash-Length-Extension-Schwäche aller Merkle–Damgaard-Hashes (MD5, SHA-1, SHA-2), sobald sie naiv als hash(secret‖data)-MAC verwendet werden.

Warum genau diese Anwendung angreifbar ist

Zwei Designfehler zusammen ergeben den Exploit

Fehler 1

Kein HMAC, keine Domain-Separation

Weder Längenprüfung noch ein Präfix/Suffix, das Length-Extension verhindern würde. Crypto.a() ist die einzige Prüfschicht.

Fehler 2

Letzter user=-Wert gewinnt

Crypto.b() parst key=value&... und überschreibt bei jedem weiteren user=-Treffer den vorherigen. Ein angehängtes &user=admin gewinnt also automatisch.

Angriffspfad

Von der Sample-Antwort zum Admin-Token

1
Sample beschaffen
Ohne jede Vorbereitung, keine Secret-Kenntnis nötig:
java -jar vault.jar --sample → message = "user=guest" (hex) → mac = SHA256(secret‖"user=guest")
2
Secret-Länge schätzen
Crypto.f() würde die Länge exakt verraten (rotateRight(rotateLeft(n,3),3) == n, reine Tarnung), ist aber im CLI-Pfad nie aufrufbar. Also: kleiner Scanbereich plausibler Längen (z.B. 0–64 Byte) — kein Brute-Force auf den MAC, nur auf eine kleine Ganzzahl.
3
Hash-State aus dem MAC rekonstruieren
Die 64 Hex-Zeichen des MAC sind die acht 32-Bit-Worte des SHA-256-Zustands nach dem letzten Block. Eine eigene SHA-256-Kernroutine, mit diesem Zustand statt der Standard-IV initialisiert, kann von dort aus weiterrechnen.
4
Padding einfügen, Suffix anhängen
Für jede geratene Secret-Länge L: das SHA-256-Padding von secret‖message (Länge L + len(message)) korrekt berechnen, dann &user=admin als neuen Block verarbeiten.
forged_message = message ‖ padding(L + len(message)) ‖ "&user=admin" forged_mac = weiterberechneter Hash-Zustand als Hex
5
Gegen die echte JAR testen
Alle Kandidaten aus Schritt 2 durchprobieren, bis einer Access granted. liefert. Die MAC-Werte selbst sind für jede Länge deterministisch vorausberechnet — es wird nur die Länge geraten, nicht der kryptographische Teil.
java -jar vault.jar <forged_hex> <forged_mac> → Access granted. → FLAG{h4sh_l3ngth_3xt3ns10n_pwn3d}
Der Nebenweg

Secret direkt aus dem Bytecode extrahieren

Bei einer rein lokal, offline lauffähigen JAR muss jedes Geheimnis, das das Programm selbst braucht, irgendwo in der Datei liegen — das lässt sich durch Verschleierung verzögern, aber nicht grundsätzlich verhindern.

1
Loader-Schlüssel rekonstruieren
javap -c -p -v auf Main.class/Main$a.class + Manifest lesen → vier Fragmente, per SHA-256 kombiniert (_deriveKey in Python nachbauen).
2
Crypto.class.encrypted entschlüsseln
Byte-Reverse + XOR mit dem berechneten Schlüssel — der Algorithmus liegt unverschlüsselt im Loader-Code direkt daneben.
3
Secret-Fragmente auslesen und kombinieren
Vier weitere Fragmente in Crypto.class, ebenfalls per SHA-256 verdichtet → das eingebettete Secret liegt im Klartext vor.
4
Eigenen, regulären MAC berechnen
Mit dem bekannten Secret braucht es keine Length-Extension mehr — ein normaler SHA256(secret‖"user=admin") reicht, und die JAR akzeptiert ihn genauso.
java -jar vault.jar <hex "user=admin"> <regulärer mac> → Access granted.

Der eigentliche Fix

Wie man das MAC-Schema tatsächlich repariert

1

HMAC-SHA256 statt Secret-Prefix-Hash

HMAC(secret, message) ist durch die doppelte Hash-Verschachtelung (inner/outer Padding, RFC 2104) konstruktiv gegen Length-Extension immun — kein Verschleierungs-Trick, sondern ein echter Fix.

2

Alternativ: SHA-3/Keccak

Sponge-Konstruktion statt Merkle–Damgaard — selbst ein naives SHA3(secret‖message) ist nicht von Haus aus length-extension-anfällig.

3

Strengeres Rollen-Parsing

Doppelte user=-Keys als Fehler behandeln statt stillschweigend zu überschreiben — Verteidigung in der Tiefe, behebt aber nicht die Hash-Schwäche selbst.

Zusammenfassung

Zwei Wege zur Flag, ein Lernziel

Hash-Length-Extension (beabsichtigt)

  • Keine Kenntnis von Secret oder Flag-Interna nötig
  • Erfordert Verständnis von SHA-256-Padding und -Zustand
  • Funktioniert allein über öffentlich sichtbares Verhalten (--sample)
  • Der einzige Weg, der ganz ohne Bytecode-Reversing von Crypto auskommt

Secret-Extraktion (Nebenweg)

  • Erfordert vollständiges Entschlüsseln von Crypto.class
  • Erfordert Kombination von acht Schlüsselfragmenten über zwei Klassen
  • Kein Kryptografie-Wissen über Hash-Interna nötig, nur sorgfältiges Bytecode-Lesen
  • Bleibt bei reiner Offline-Verteilung strukturell nicht vollständig verhinderbar
